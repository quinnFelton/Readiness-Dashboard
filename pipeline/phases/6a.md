# Phase 6a — Dashboard and trends screens
PLAN refs: §9 (/dashboard, /dashboard/trends, hero chart, charts), §8.3 (quadrant states and colors).
- Shared parameterized chart component in apps/web/src/components/charts (line/area, multiple series, optional colored state bands for quadrant periods, sparse-data safe).
- /dashboard: current fatigue/fitness state as the hero (state, insight text, since when), hero chart of EF peak-20 vs HRV and resting HR on a shared timeline with quadrant bands, and the secondary readiness score.
- /dashboard/trends: per-metric breakdown (EF peak-20, EF overall, HRV, resting HR) with 7d vs 28d context.
- Empty state that sends a new user to /settings/connections.
- Reusable `AthleteDashboard` component taking a userId, so 6b's admin drill-down can render the same view.

## Feedback and event logging (PLAN §8.7 — owner decision 2026-10-04)
Phase 5b provides `/api/v1/feedback/:userId` and `/api/v1/athlete-events/:userId`. If they aren't on main yet, code against the contract in pipeline/phases/5b.md and mock them in your tests.
- **Rating insights:** thumbs up/down on the hero insight, and on each flagged state in the trends view. The vote is recorded against the classifier id and as-of date shown. Show the current vote, and allow changing it or adding an optional short comment.
- **Event log:** a small "Log event" form (date, type: illness / injury / race / planned rest, optional notes) and a list of recent events with delete.
- **On the chart:** show logged events as markers on the hero chart timeline.
- **Coach view:** keep all of this inside `AthleteDashboard`, so the coach drill-down (6b) gets it too. A master viewing an athlete can vote and log events for that athlete.
- **Data handling:** never log notes or comments to the console or analytics.

# Phase 2 — Connection framework (before any provider)
PLAN refs: §6 (whole section), §7 `provider_connections`, `connection_configs`, `daily_metrics`, `activity_efforts`, `webhook_events`, §12, §13.
You start from the phase-1 branch, so users/auth already exist.
Build:
- Migrations for provider_connections, connection_configs, daily_metrics, activity_efforts, webhook_events (exactly PLAN §7, including indexes and unique keys).
- packages/shared-types: NormalizedDailyMetric, NormalizedActivityEffort, ConnectionRole, ProviderConnection.
- packages/provider-adapters: `ProviderAdapter<T>` interface, a registry keyed by provider + role, and a fake in-memory adapter used only in tests.
- apps/api crypto interface `TokenCipher` (encrypt/decrypt) with a local AES-256-GCM implementation keyed from TOKEN_ENCRYPTION_KEY, and a KMS implementation stub with the same interface.
- ConnectionConfigService: set the single activity source, set ordered daily-metrics sources (priority), read precedence per metric type.
- SyncService orchestrator that looks up active adapters per user from connection_configs and upserts normalized rows idempotently. It must contain no provider-specific code.
- Routes: POST /connections/:provider/start and GET /connections/:provider/callback dispatching to the registered adapter; DELETE /connections/:provider (deletes tokens AND that provider's derived rows); GET/PUT /connections/config.
Tests: registry lookup, precedence resolution (Oura-preferred default, overridable), idempotent upsert run twice = one row, disconnect deletes data, only one activity source allowed.

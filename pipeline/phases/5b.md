# Phase 5b — Fatigue/fitness classifier service + trends/scores API
PLAN refs: §6 (FatigueFitnessService, TrendService, /scores, /trends routes), §7 `trends`, `readiness_scores`, §8.2–8.4, §8.6.
Use @rd/scoring-engine for all math; this phase is orchestration and persistence only.
- Migrations for readiness_scores and trends (PLAN §7) if not already present. Note: `window` is a reserved word in Postgres — quote it or name the column `trend_window` and document the deviation.
- Trigger: after either a daily-metrics or activity sync completes for a user, check whether both an EF trend and a recovery trend now exist for the affected window; if so (re)run the classifier and upsert trends rows. Otherwise do nothing.
- Daily metric precedence: read from ConnectionConfigService, never average sources.
- readiness_scores: simple secondary blend of that day's recovery metrics (keep it simple, weights in config).
- Routes: GET /api/v1/scores/:userId?range=28d and GET /api/v1/trends/:userId with requireSelfOrMaster; these only read precomputed rows.
- Classifier thresholds come from config (env or a config table), not code constants.
Tests: trigger fires only when both trends exist, precedence respected, recompute is idempotent, a user cannot read another user's trends.

## Side-by-side classifiers and derivers (PLAN §8.7, §8.8 — owner decision 2026-10-04: build the plumbing now)
The registries already exist: `createClassifierRegistry`, `classifyAll`, `TrendClassifier` and `TrendInputs`, plus `createDeriverRegistry` and `DEFAULT_*_ID`, all from @rd/scoring-engine. Migration `*_phase-fw_*` already created the `classifiers` and `derivers` tables (one `is_default` row each) and `activity_efforts.deriver_id`.
- **`trends` table:** add `classifier_id TEXT NOT NULL REFERENCES classifiers(id)`, and include it in the trends natural key/unique constraint, so variants never collide.
- **Classifier runs:** FatigueFitnessService runs EVERY registered classifier on each compute pass with the same `TrendInputs`, via `classifyAll`, and upserts one row per classifier.
- **Which deriver feeds the EF baseline:** only the default deriver's `activity_efforts` rows: `deriver_id = (SELECT id FROM derivers WHERE is_default)`. Never mix derivers in one series.
- **What the routes return:**
  - `/scores` and `/trends` return only the `is_default` classifier's rows by default. Read the flag from the DB, not the code constant.
  - Add an optional `?classifier=<id>` for master users only, to compare variants. A plain user asking for a non-default classifier gets 403.
- **Configuration:** the runtime default comes from the DB flags. If a flagged id isn't registered in code, fail loudly; don't silently fall back.
- **Tests:**
  - two classifiers produce two rows per window;
  - only the default's rows are returned to a user;
  - only default-deriver efforts feed the EF series;
  - recompute stays idempotent for every classifier.

## Feedback and outcome tracking for comparing classifiers (PLAN §8.7 — owner decision 2026-10-04: build now)
These two features make "which classifier is more accurate" measurable: athletes rate insights, and coaches or athletes log real events. Put the code in `apps/api/src/feedback/**`, `apps/api/src/athlete-events/**` and `apps/api/src/comparison/**`. Export each router; do NOT edit `apps/api/src/app.ts`, because the integrator mounts them.

**Migration (`*_phase-5b_*`):**
- `insight_feedback`:
  - columns: `user_id` (the athlete) → users ON DELETE CASCADE; `classifier_id` → classifiers; `as_of` DATE (the trend's date); `state` at vote time; `vote SMALLINT CHECK (vote IN (-1, 1))`; optional short `comment`; `voted_by` → users; `created_at` / `updated_at`;
  - key: UNIQUE (user_id, classifier_id, as_of, voted_by), so a re-vote updates instead of duplicating.
- `athlete_events`:
  - columns: `user_id` → users ON DELETE CASCADE; `date`; `event_type CHECK IN ('illness','injury','race','planned_rest')`; `notes`; `created_by` → users; `created_at`;
  - index on (user_id, date).
- Both tables hold health-adjacent data: never log `notes` or `comment` (CLAUDE.md rule 6), and per-user delete (§12) must cover them.

**Routes (all `requireSelfOrMaster` on `:userId`):**
- `PUT /api/v1/feedback/:userId`: body `{ classifierId, asOf, vote, comment? }`. Validate that a `trends` row exists for that user, classifier and date, and record its `state`.
- `GET /api/v1/feedback/:userId?range=`: the user's votes, for showing the current thumbs state.
- `GET`, `POST` and `DELETE /api/v1/athlete-events/:userId[/:id]`: delete only within that user.

**Master-only comparison routes** (403 for plain users, enforced server-side):
- `GET /api/v1/comparison/classifiers?range=90d`. Per classifier id:
  - **agreement:** up votes, down votes, and agreement rate;
  - **backtest against `athlete_events`:** for illness and injury events, how many were preceded by an `overreaching_risk` or `acute_fatigue` flag within `LEAD_DAYS`, and how many such flags had no event within `LEAD_DAYS` after them (false alarms);
  - **which one is the default.**
  - Put `LEAD_DAYS` and the counted event and state types in config (rule 9).
  - The backtest is pure: put it in `@rd/scoring-engine` as a new file, with tests, and leave existing engine files alone.
- `PUT /api/v1/comparison/classifiers/:id/default`: promote a registered classifier to default in one transaction. All variants already have rows, so no recompute is needed. Refuse an id that isn't in the code registry.
- `GET /api/v1/comparison/derivers`: list the derivers with their default flag. No promotion endpoint for derivers yet: switching the deriver changes the EF series and needs a recompute, so leave a TODO.

**Tests:**
- feedback upsert idempotency and vote validation;
- feedback rejected for a non-existent trend;
- athlete-event CRUD isolated per user;
- a user can't read or write another user's data;
- the comparison routes return 403 for non-masters;
- backtest numbers against a hand-checked fixture;
- promotion leaves exactly one default;
- notes and comments never logged.

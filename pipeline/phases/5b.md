# Phase 5b — Fatigue/fitness classifier service + trends/scores API
PLAN refs: §6 (FatigueFitnessService, TrendService, /scores, /trends routes), §7 `trends`, `readiness_scores`, §8.2–8.4, §8.6.
Use @rd/scoring-engine for all math; this phase is orchestration and persistence only.
- Migrations for readiness_scores and trends (PLAN §7) if not already present. Note: `window` is a reserved word in Postgres — quote it or name the column `trend_window` and document the deviation.
- Trigger: after either a daily-metrics or activity sync completes for a user, check whether both an EF trend and a recovery trend now exist for the affected window; if so (re)run the classifier and upsert trends rows. Otherwise do nothing.
- Daily metric precedence: read from ConnectionConfigService, never average sources.
- readiness_scores: simple secondary blend of that day's recovery metrics (keep it simple, weights in config).
- Routes: GET /api/v1/scores/:userId?range=28d and GET /api/v1/trends/:userId with requireSelfOrMaster; these only read precomputed rows.
- Classifier thresholds come from config (env or a config table), not code constants.
Tests: trigger fires only when both trends exist, precedence respected, recompute is idempotent, a user cannot read another user's trends.

## Side-by-side classifiers and derivers (PLAN §8.7, §8.8 — owner decision 2026-10-04: build the plumbing now)
The registries already exist: `createClassifierRegistry`, `classifyAll`, `TrendClassifier` and `TrendInputs`, plus `createDeriverRegistry` and `DEFAULT_*_ID`, all from @rd/scoring-engine. Migration `*_phase-fw_*` already created the `classifiers` and `derivers` tables (one `is_default` row each) and `activity_efforts.deriver_id`.
- **`trends` table:** add `classifier_id TEXT NOT NULL REFERENCES classifiers(id)`, and include it in the trends natural key/unique constraint, so variants never collide.
- **Classifier runs:** FatigueFitnessService runs EVERY registered classifier on each compute pass with the same `TrendInputs`, via `classifyAll`, and upserts one row per classifier.
- **Which deriver feeds the EF baseline:** only the default deriver's `activity_efforts` rows: `deriver_id = (SELECT id FROM derivers WHERE is_default)`. Never mix derivers in one series.
- **What the routes return:**
  - `/scores` and `/trends` return only the `is_default` classifier's rows by default. Read the flag from the DB, not the code constant.
  - Add an optional `?classifier=<id>` for master users only, to compare variants. A plain user asking for a non-default classifier gets 403.
- **Configuration:** the runtime default comes from the DB flags. If a flagged id isn't registered in code, fail loudly; don't silently fall back.
- **Tests:**
  - two classifiers produce two rows per window;
  - only the default's rows are returned to a user;
  - only default-deriver efforts feed the EF series;
  - recompute stays idempotent for every classifier.
